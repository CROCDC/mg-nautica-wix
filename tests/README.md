# Test suite

The cross-project testing strategy, ported to this Next.js + Wix headless storefront.
There is no database and no authenticated area here, so the layers are:

| Layer | File | What it defends |
| --- | --- | --- |
| Overflow guard | `overflow-detection.spec.ts` | The validity of the responsive layer |
| Responsive / visual | `responsive.spec.ts` | Every public page × every viewport, + the screenshot baseline |
| E2E | `e2e-catalog.spec.ts`, `e2e-filters.spec.ts`, `e2e-product.spec.ts`, `e2e-navigation.spec.ts` | Every user-facing flow |
| HTTP | `routes.spec.ts` | Status codes, legacy redirects, robots.txt, the edge middleware |
| Metadata | `metadata.spec.ts` | Titles, canonicals, Open Graph — the invisible failures |
| Unit | `unit/wix-mapping.spec.ts` | The pure mapping/formatting logic in `lib/` |
| Live smoke | `live/wix-contract.spec.ts` | That the real Wix API contract still holds |

`helpers/` holds shared non-spec code (Playwright only collects `*.spec.ts`).

### Two areas that are easy to under-test

**The filter bar** (`e2e-filters.spec.ts`) is the densest logic on the site, and most of
it is invisible to a happy-path test: Enter-to-submit goes through the same `onSubmit` as
the button but is the path people actually use; `toNum` treats `0`, `-5` and `abc` as
"no bound"; the `✕` button keys off live field state, not the URL; `SearchBox` is keyed
by `basePath` so switching category resets it. Each of those is a branch with its own test.

**Anything below 768px.** The nav collapses entirely behind the burger (`.nav-links` is
`display: none` until `.open`), and the filter bar re-flows. A desktop-only suite cannot
reach either code path, so both files end with a `375px` block that drives the real
controls — that is where the filter-bar overflow bug would have shown up as a button the
visitor simply cannot tap.

## Running

```bash
npm test            # everything except the live smoke suite
npm run test:live   # the live smoke suite only (needs .env.local)
npm run typecheck   # app + tests
```

Both scripts run `next build` first and serve the production build — `next start`, not
`next dev` — so the tests exercise what actually ships.

## Why the Wix API is mocked, and where

Every page is `force-dynamic` and `lib/wix.ts` is `server-only`, so the Wix calls happen
**in the server process**. Playwright's `page.route()` only sees browser traffic and
would never intercept them, so the seam lives inside the Next process instead:
`mock/wix-http-mock.mjs` patches `globalThis.fetch` and is loaded with `--import` before
Next boots.

It mocks the **boundary** — the `wixapis.com` exchanges — and nothing inside it. The real
SDK, the real mapping, the real SSR and the real routing all still run.

`mock/cassette.json` holds those recorded exchanges and is committed. That is what makes
the suite deterministic and credential-free, and what stops the screenshot baseline from
churning every time the owner edits the catalog in the Wix dashboard.

A replay miss **throws** rather than falling back to the network — a silent fallback
would quietly make the whole suite depend on live credentials again.

### Re-recording

```bash
npm run test:record   # needs the real credentials in .env.local
```

Boots the production server in `record` mode, walks the catalog-backed pages, and
rewrites `mock/cassette.json` plus `mock/fixture-meta.json` (the product slugs the specs
use). Access tokens are redacted on the way in. Re-record when the Wix API contract
changes or when the specs need catalog data the cassette does not have — not routinely.

The live smoke suite is the counterweight: it is the only thing that would notice Wix
changing their contract, so it is worth running before a release.

## Screenshots

`responsive.spec.ts` writes a full-page screenshot per page × viewport into
`screenshots/`, and **they are committed** — they are the visual baseline, and diffs
surface in review. They are regenerated by any `npm test` run.

Two things make them trustworthy:

- **Reduced motion.** The site reveals content with an `IntersectionObserver`, so in a
  full-page screenshot everything below the fold would sit at `opacity: 0`. The site
  already honours `prefers-reduced-motion: reduce` by forcing those elements visible, so
  the tests ask for it — a supported user setting, not a test-only hack.
- **Settled counters.** The hero stat counters animate up from 0 on mount, so the
  screenshot waits for their text to stop changing; otherwise a different number would be
  baked into the baseline on every run.

The third-party Next Tech footer widget is blocked at the browser boundary (see
`fixtures.ts`) so their deploys cannot churn our baseline and `networkidle` never waits on
someone else's server. The Wix image CDN is deliberately **not** blocked: the boat photos
are content, and a baseline full of broken images would be worth far less.

## Regressions this suite was written against

Two real bugs surfaced while building it, both now fixed and both guarded:

- **Catalog filter bar overflowed the viewport** (53px at 375, 14px at 414).
  `.filter-bar` carries `flex-wrap: wrap` for its row layout while the category page
  overrides the direction to `column` inline — and a *wrapping column* flex container
  sizes each line to its content, not to the container. Guarded by `responsive.spec.ts`.

- **`/category/<unknown>` answered 200** with the not-found page in the body. The page
  rendered its shell before resolving the category, so the status was already on the wire
  when `notFound()` fired inside the streamed results — a soft 404 for crawlers. Fixed by
  awaiting the lookup in the page body, as `/product-page` already did. Guarded by
  `routes.spec.ts`, which asserts the **status**, not just the body — a body-only
  assertion would have passed the whole time.

  The trade-off is measurable: the shell now waits on the categories query, so TTFB on a
  category page goes from ~0.14s to ~0.29s against live Wix, while total page time is
  unchanged (~1.24s vs ~1.29s). Prefetching the catalog before the lookup would claw back
  ~0.13s of total time, but it fires a full products query on every bogus category URL —
  the exact upstream waste `middleware.ts` and `robots.ts` exist to prevent — so it was
  left out.
